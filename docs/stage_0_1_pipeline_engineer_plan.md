# Stage 0-1 Pipeline Engineer Plan

## Что агент понял

Проект пересобирает старую документно-хаотичную медицинскую базу знаний в сущностную структуру. Новая единица знания - медицинская сущность, а старые документы являются источниками.

Роль Pipeline Engineer отвечает за каркас проекта, CLI, чтение `documents.csv`, парсинг Editor.js, генерацию `doc_id`, сохранение промежуточных артефактов, базовые схемы данных и запуск этапов по отдельности.

Ключевые требования:

- каждый этап должен запускаться отдельно;
- все артефакты должны быть воспроизводимыми и пригодными для повторного запуска;
- нужен `--limit` для dry-run на малом наборе документов;
- ошибки отдельных документов не должны останавливать весь прогон;
- исходные данные нельзя удалять;
- LLM-вызовы не входят в parsing и не должны выполняться без явной команды этапа и кэширования;
- форматы JSON/JSONL/CSV должны быть описаны в коде, схеме или документации;
- для важных преобразований нужны тесты или минимальные проверки.

## Какие артефакты должен создать

Минимальная зона ответственности Pipeline Engineer:

- `data/parsed/parsed_documents.jsonl`;
- `data/parsed/document_blocks.jsonl`;
- базовая структура `data/` для последующих этапов;
- конфигурация пайплайна;
- CLI-команды этапов:
  - `parse`;
  - `tag`;
  - `normalize`;
  - `extract-evidence`;
  - `compile-articles`;
  - `build-folders`;
  - `validate`;
  - `report`;
- базовые схемы или dataclass/model-описания для документов и блоков;
- логи и базовый `data/reports/run_report.json`;
- тесты на парсинг Editor.js и генерацию `doc_id`.

## Какие файлы планирует изменить

Текущий файл плана:

- `docs/stage_0_1_pipeline_engineer_plan.md`.

Предполагаемые файлы при реализации этапа:

- `main.py` или новый CLI-entrypoint;
- модуль чтения CSV;
- модуль парсинга Editor.js;
- модуль записи JSONL/CSV/JSON;
- модуль схем данных;
- модуль отчетов и логирования;
- тесты для парсинга и генерации идентификаторов;
- документация по запуску и форматам артефактов.

Точная структура модулей должна быть выбрана после осмотра текущего кода проекта.

## Какие риски видит

- В `documents.csv` может не быть стабильного ID, поэтому генерация `doc_id` должна быть детерминированной по порядку входных строк.
- `content` может быть пустым, битым JSON или нестандартным Editor.js; такие документы нужно сохранять со статусом ошибки или частичного парсинга.
- Editor.js-блоки могут содержать таблицы, списки, вложенные структуры и HTML; чистый текст нужно извлекать без молчаливой потери блока.
- При повторном запуске нельзя случайно перемешивать старые и новые артефакты без явной политики overwrite/resume.
- Нельзя смешать parser-логику с будущими LLM-вызовами, иначе этапы станут невоспроизводимыми и дорогими.
- Форматы артефактов должны быть стабильными, иначе downstream-агенты будут вынуждены адаптироваться к неявным изменениям.
