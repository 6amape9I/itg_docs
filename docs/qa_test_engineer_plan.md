# QA / Test Engineer Plan

## Что агент понял

Проект пересобирает медицинскую базу знаний из старых документов в сущностные статьи. Главный принцип: финальная единица знания - медицинская сущность, а старые документы являются источниками.

QA / Test Engineer отвечает за независимую проверку этапов пайплайна, качество артефактов, тестовые фикстуры, регрессионный контроль и summary report. Нельзя доверять результатам этапов без формальных проверок.

## Артефакты, которые должен создать QA

- Набор искусственных документов для тестов:
  - простой документ;
  - документ с двумя сущностями;
  - битый Editor.js;
  - пустой `content`;
  - документ с таблицей;
  - документ с повторяющимся названием.
- Проверки валидности JSONL / CSV / JSON.
- Проверки уникальности `doc_id`, `block_id`, `tag_id` и других ключевых идентификаторов.
- Проверки соответствия цитат исходному тексту.
- Проверки, что `folder_manifest.json` ссылается на существующие файлы.
- Summary report по качеству артефактов.
- Feedback-файл по завершении работы: `docs/qa_test_engineer_feedback.md`.

## Файлы, которые планируется изменить

Точный список зависит от текущей структуры проекта. Предварительно ожидаемые зоны изменений:

- `tests/` - тесты и фикстуры.
- `data/` или отдельная тестовая директория - синтетические входные данные, если это принято в проекте.
- `src/` или существующий пакет пайплайна - валидаторы и отчётность, если они ещё не реализованы.
- `docs/qa_test_engineer_feedback.md` - итоговый отчёт QA.

## Риски

- Форматы артефактов могут быть частично не реализованы или отличаться от требований.
- Часть проверок может требовать данных последующих этапов, которых ещё нет.
- Проверка цитат зависит от нормализации текста: переносы строк, пробелы и HTML могут давать ложные отрицания.
- Manifest и quotes могут появиться только на поздних этапах, поэтому проверки должны корректно различать отсутствующий этап и ошибочный артефакт.
- Нельзя добавлять внешние медицинские знания или исправлять содержимое данных вместо проверки их качества.
