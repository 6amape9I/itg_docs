# LLM Orchestrator Engineer Plan

## Что агент понял

Проект пересобирает медицинскую базу знаний из старых документов в сущностные статьи. Роль LLM Orchestrator Engineer отвечает не за медицинскую логику и не за финальные статьи, а за контролируемое использование LLM как сервиса внутри пайплайна.

Ключевые ограничения:

- нельзя вызывать LLM без кэширования запроса;
- каждый prompt обязан иметь `prompt_version`;
- каждая схема ответа обязана иметь `schema_version`;
- нельзя использовать `latest`-алиасы моделей;
- LLM-ответы нужно валидировать как JSON;
- при невалидном ответе допустимы ограниченные ретраи;
- после исчерпания ретраев item должен получать статус `failed`, а весь прогон не должен падать;
- нужно сохранять `model_id`, `usage`, `latency`, `finish_reason` и оценку стоимости;
- нельзя отправлять данные в LLM без явной команды этапа;
- чувствительный контент не должен попадать в лишние логи, если появится режим redaction.

## Какие артефакты должен создать

Планируемые артефакты LLM-слоя:

- конфигурация провайдера OpenRouter и явных моделей без `latest`;
- клиент LLM с ретраями, таймаутами, fallback-моделями и structured outputs там, где это поддерживается;
- дисковый кэш LLM-запросов, пригодный для resume после сбоя;
- версии промптов для этапов, использующих LLM;
- JSON Schema для ответов LLM с `schema_version`;
- журнал вызовов с метаданными: `model_id`, `usage`, `latency`, `finish_reason`, стоимость, статус;
- статусы обработки items: `ok`, `cached`, `retrying`, `failed`;
- минимальные тесты или проверки для кэша, валидации JSON и обработки невалидного ответа.

## Какие файлы планирует изменить

Точный список будет уточнён после осмотра существующего кода. Предварительно ожидаются изменения в следующих областях:

- `main.py` или будущий CLI-модуль, если в проекте ещё нет CLI;
- новые модули для LLM-клиента, кэша, промптов, схем и логирования;
- конфигурационные файлы для моделей, лимитов ретраев и путей артефактов;
- тесты или минимальные validation scripts;
- документация в `docs/`.

## Риски

- В проекте пока нет выраженной архитектуры, поэтому есть риск преждевременно закрепить неудачную структуру модулей.
- OpenRouter API и поддержка structured outputs зависят от выбранной модели; нужна явная конфигурация возможностей модели.
- Стоимость вызова может быть неточной без актуальной таблицы цен, поэтому расчёт должен быть изолирован и помечен как estimate.
- Медицинские тексты могут содержать чувствительные данные; логирование должно быть метаданным по умолчанию.
- Невалидные LLM-ответы нельзя пропускать дальше без статуса ошибки и диагностического артефакта.

## Допущения

- До отдельной команды на запуск LLM фактические сетевые LLM-вызовы не выполняются.
- Если ключи OpenRouter отсутствуют, код должен уметь работать в dry-run или mock-режиме для тестов.
- Redaction-режим может быть добавлен как конфигурационный флаг, даже если пока не используется.
