# Архитектурное решение: Gemini 3 Flash как основной кандидат для этапа тегирования

## Контекст

На этапе тегирования DeepSeek V4 Flash показал приемлемую цену и валидный JSON, но столкнулся с неприемлемой проблемой скорости и 429 на OpenRouter/provider route. Параллельный прогон по нескольким ключам не решил проблему: лимит выглядит общим для маршрута/модели/аккаунта/provider capacity.

Параллельно есть практическое наблюдение владельца проекта: коллега с тем же OpenRouter-ключом смог отправить около 1500 запросов к Gemini 3 Flash за 1 час. Это сильный сигнал, что проблема не в ключе и не в платности аккаунта, а в конкретном маршруте DeepSeek через OpenRouter.

## Предварительный расчёт

Фактический JSONL-прогон DeepSeek Flash на первых примерах показал:

- 41 успешная запись DeepSeek Flash;
- средняя стоимость записи около $0.0004456;
- среднее потребление около 1754 prompt tokens и 714 completion tokens на документ;
- средняя latency live-запросов около 42 секунд;
- фактическая wall-clock скорость диагностического DeepSeek-прогона с 429/recovery около 20 документов/час.

Поэтому при текущей DeepSeek-схеме:

- 16 181 документов при 20 документов/час — около 812 часов, то есть около 34 дней;
- даже идеальная последовательная DeepSeek-схема без 429 при 42 секундах latency — около 85 документов/час, то есть около 190 часов на корпус;
- стоимость DeepSeek-тегирования всего корпуса низкая, около $7–10, но скорость неприемлема.

Если Gemini 3 Flash реально выдерживает 1500 запросов/час:

- one document per request: 16 181 / 1500 ≈ 10.8 часа;
- batch size 5: до 7500 документов/час, весь корпус ≈ 2.2 часа;
- batch size 10: до 15 000 документов/час, весь корпус ≈ 1.1 часа.

По стоимости при том же среднем token profile Gemini 3 Flash оценивается примерно в $0.0030 на документ и около $49 на полный корпус. С запасом на reasoning/output/retries бюджет $100 на этап тегирования выглядит достаточным.

## Решение

Для полировки этапа тегирования считать Gemini 3 Flash не просто экспериментом, а основным кандидатом на замену DeepSeek V4 Flash.

Основная модель для нового benchmark:

```text
google/gemini-3-flash-preview
```

DeepSeek V4 Flash временно переводится в baseline/reference, а не в основной production route.

## Что нельзя делать

Нельзя сразу запускать весь корпус на Gemini без 200-document benchmark и QA-аудита.

Нельзя смешивать результаты Gemini и DeepSeek в одном active output.

Нельзя отдавать в нормализацию файл, где есть дубли по `doc_id`, старые модели, diagnostic records или разные prompt/schema versions.

Нельзя считать 1500 запросов/час гарантированной скоростью для наших длинных медицинских документов: это практический ориентир, который нужно проверить на нашем payload.

## Критерий перехода на Gemini как primary

Gemini 3 Flash становится primary tagging model, если на одном и том же наборе 200 документов:

1. successful documents >= 95% непустых документов;
2. invalid JSON = 0 или все ошибки успешно восстановлены retry;
3. HTTP 429 не блокирует прогон и восстанавливается автоматически;
4. средняя скорость минимум 300 документов/час в one-doc режиме или минимум 1000 документов/час в batch режиме;
5. доля цитат `found` + `fuzzy` >= 85%, а `not_found` <= 15%;
6. QA не находит критического падения качества тегов относительно DeepSeek baseline;
7. итоговая стоимость 200-doc benchmark укладывается в разумный диапазон и масштабируется на корпус меньше чем $100 для tagging stage.

## Ожидаемое дальнейшее направление

Если Gemini 3 Flash проходит benchmark, следующий production-план:

```text
model = google/gemini-3-flash-preview
batch_size = 5 сначала
max_inflight = 1 сначала
после 20 успешных batch без 429: max_inflight = 2
после 100 успешных batch без 429: batch_size = 8-10
```

Полный корпус запускать только через active/history split, LLM-cache, adaptive global rate limiter, run report и QA validation.
