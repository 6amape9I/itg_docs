Название проекта

Первичная пересборка медицинской базы знаний из документно-хаотичной структуры в сущностную структуру.

Цель проекта

Исходная база содержит около 16 000 документов. Каждый старый документ может содержать знания по нескольким темам, а знания об одной сущности могут быть размазаны по множеству документов.

Цель — построить воспроизводимый пайплайн, который:

извлекает чистый текст из Editor.js;

размечает каждый старый документ ключевыми медицинскими сущностями;

нормализует теги и схлопывает синонимы;

строит связь canonical_tag → source_documents;

извлекает из старых документов только релевантные evidence-фрагменты по каждой сущности;

создаёт по каждой финальной сущности новую структурированную статью в формате Editor.js JSON;

создаёт JSON с цитатами, доказывающими утверждения статьи;

формирует иерархию папок и manifest для загрузки документов в систему.

Главный принцип

Новая единица знания — не старый документ, а сущность.

Сущностью может быть болезнь, лекарство, БАД, симптом, медицинское изделие, процедура, диагностический метод, орган/система организма или другая самостоятельная медицинская тема.

Старые документы являются источниками. Финальные документы являются пересобранными сущностными статьями.

Не цель текущего этапа

Не нужно сейчас генерировать 30–50 вопросов к каждому документу.

Не нужно сейчас добиваться идеального графа знаний.

Не нужно сейчас вручную проверять каждую медицинскую сущность.

Не нужно сейчас создавать идеальный энциклопедический медицинский справочник из внешних знаний.

Запрещено добавлять в статьи факты, которых нет в исходных документах или evidence-фрагментах.

Входные данные

Основной входной файл:

documents.csv

Ожидаемые колонки:

name
description
content

name используется как важный контекст документа.

description на первом этапе считается бесполезным и не используется, но не удаляется из исходных данных.

content содержит документ в формате Editor.js JSON.

Если стабильного ID нет, пайплайн обязан создать doc_id.

Выходные артефакты

Минимальный набор артефактов:

data/parsed/document_blocks.jsonl

data/tagging/document_tags_raw.jsonl

Все артефакты должны быть воспроизводимыми, валидируемыми и пригодными для повторного запуска.

Этап 0. Инфраструктура пайплайна

Нужно создать проектную структуру, конфиги, схемы данных, CLI-команды, логирование, обработку ошибок, кэширование LLM-ответов и отчёты.

Пайплайн должен уметь запускаться по этапам:

parse
tag
normalize
extract-evidence
compile-articles
build-folders
validate
report

Должен быть dry-run режим на малом количестве документов:

--limit 100

Должна быть возможность продолжить выполнение после сбоя без повторной оплаты уже выполненных LLM-запросов.

Этап 1. Парсинг Editor.js

Нужно прочитать documents.csv, распарсить content, извлечь чистый текст и сохранить блоковую карту.

Каждый документ должен получить:

{
  "doc_id": "doc_000001",
  "name": "Название документа",
  "description": "...",
  "content_hash": "sha256...",
  "parse_status": "ok",
  "clean_text": "Очищенный текст документа...",
  "text_length_chars": 12345,
  "blocks_count": 12
}

Каждый блок должен получить:

{
  "doc_id": "doc_000001",
  "block_id": "b_000001",
  "block_index": 0,
  "block_type": "header",
  "text": "Гастрит",
  "raw": {}
}

Если блок не удалось распарсить, он не должен молча исчезать. Его нужно сохранить с parse_status = "partial" или parse_status = "failed".

Этап 1.5. Первичное тегирование документов

На вход LLM передаётся название документа и очищенный текст.

LLM должна вернуть строгий JSON со списком основных сущностей документа.

Теги должны выделять только ключевые сущности, а не все встречающиеся слова. Например, если документ про медицинские перчатки и гастрит, теги: Медицинские перчатки, Гастрит. Не нужно добавлять “лечение”, “инструкция”, “профилактика”, если это не самостоятельная сущность.

Схема ответа:

{
  "doc_id": "doc_000001",
  "entities": [
    {
      "surface": "гастрит",
      "canonical_candidate": "Гастрит",
      "entity_type": "disease",
      "is_primary": true,
      "confidence": 0.94,
      "evidence_quotes": [
        "Короткая цитата из документа, подтверждающая наличие сущности"
      ],
      "comment": "Почему это основная сущность"
    }
  ]
}

Разрешённые entity_type:

disease
drug
supplement
symptom
medical_device
procedure
diagnostic_method
organ_or_body_system
medical_concept
other

Если сущность не медицинская и не имеет ценности для финальной базы, она не должна попадать в список тегов.

Этап 2. Нормализация тегов

Нужно собрать все сырые теги в единый список и схлопнуть синонимы.

На выходе должны быть:

tags_canonical.csv
tag_aliases.csv
document_tag_links.csv

tags_canonical.csv:

tag_id
canonical_tag
entity_type
status
confidence
created_from_aliases_count

tag_aliases.csv:

alias
tag_id
canonical_tag
entity_type
normalization_reason
confidence

document_tag_links.csv:

doc_id
tag_id
canonical_tag
entity_type
source_surface
confidence

Правила нормализации:

канонический тег должен быть самостоятельной сущностью;

синонимы схлопываются;

разные типы сущностей не схлопываются между собой;

“лечение”, “диагностика”, “профилактика”, “симптомы” не являются тегами, если они не выступают как самостоятельные сущности;

для лекарств нужно различать МНН/действующее вещество и торговое название;

для БАДов допускается сохранение коммерческого названия как отдельной сущности;

низкоуверенные и спорные случаи маркируются status = needs_review, но не должны ломать пайплайн.

Этап 3. Извлечение evidence по каждому тегу

Для каждого tag_id нужно взять все связанные исходные документы и по каждому документу отдельно извлечь релевантные фрагменты, касающиеся только этой сущности.

Нельзя просить модель “собрать всё сразу из всех документов”. Извлечение идёт по схеме:

один тег + один старый документ → список evidence items

Схема evidence item:

{
  "tag_id": "tag_000123",
  "canonical_tag": "Гастрит",
  "source_doc_id": "doc_000456",
  "source_doc_name": "Гастрит: симптомы и лечение",
  "items": [
    {
      "quote": "Дословная цитата из исходного документа...",
      "block_ids": ["b_0003"],
      "fact_type": "definition",
      "importance": "high",
      "confidence": 0.93,
      "extraction_comment": "Почему фрагмент относится к тегу"
    }
  ]
}

Разрешённые fact_type:

definition
classification
causes
risk_factors
symptoms
diagnostics
treatment
prevention
contraindications
side_effects
dosage_or_usage
storage
procedure_steps
safety
complications
when_to_seek_help
related_entities
other

Каждая цитата должна быть дословным фрагментом исходного документа. Код обязан проверить, что цитата находится в clean_text или в одном из block texts. Если точного совпадения нет, включается fuzzy matching. Если fuzzy matching не подтвердил цитату, item получает статус invalid_quote.

Статья создаётся только на основе evidence items.

Модель не имеет права добавлять внешние медицинские знания. Если evidence не покрывает раздел, раздел можно пропустить или написать “В исходных документах недостаточно данных”.

  "tag_id": "tag_000123",
  "canonical_tag": "Гастрит",
  "entity_type": "disease",
  "folder_path": "Болезни/Заболевания ЖКТ",
  "article_file": "articles/gastrit.json",
  "quotes_file": "quotes/gastrit_quotes.json"
}
Валидация качества

Обязательные проверки:

каждый doc_id уникален;

каждый блок имеет block_id;

каждый LLM-ответ валиден по JSON Schema;

каждый финальный тег имеет entity_type;

каждый финальный тег имеет хотя бы один исходный документ;

каждая статья имеет хотя бы один evidence item;

каждая цитата проверена на наличие в исходном документе;

каждый файл статьи и цитат существует в manifest;

не должно быть статей без canonical tag;

не должно быть document_tag_links на несуществующий tag_id;

не должно быть quote links на несуществующий source_doc_id.

Критерии готовности MVP

MVP считается готовым, если:

все документы из documents.csv обработаны или имеют явный parse error;

созданы parsed_documents.jsonl и document_blocks.jsonl;

получены сырые теги по документам;

создан список canonical tags и alias mapping;

построены связи document → canonical_tag;

для тегов извлечены evidence-фрагменты;

для тегов созданы статьи в Editor.js JSON;

для статей созданы quotes JSON;

создан folder_manifest.json;

создан run_report.json;

пайплайн можно перезапустить без повторной оплаты уже обработанных LLM-запросов.
