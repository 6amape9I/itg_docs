## 0. Контекст

Этап N1 уже реализован и в целом принят как технический слой подготовки нормализации. Он собрал mentions, normalized forms, auto-clusters, suspicious mentions, quote issues и отчёты.

- `unique_raw_values`: 22 710;
- `unique_normalized_values`: 22 116;
- `auto_clusters_total`: 22 993;
- `auto_clusters_review_required`: 10 285;
- `suspicious_mentions`: 25 184;

- `documents_with_tags`: 16 161;

По `normalization_n1_manifest.json`, N1 построен поверх чистого tagging-run `tagging_20260505_095008`, source provider `gemini_direct`, source model `gemini-3-flash-preview`, source prompt `tagging_v2_gemini`, source schema `document_tagging_v2`. :contentReference[oaicite:1]{index=1}

## 1. Зачем нужна N1.1

N1 сделал правильную основу, но перед N2 нужно исправить несколько проблем:

1. В `auto_clusters.csv` есть визуальные/логические дубли, например `ARX`.
2. Short aliases и abbreviations сейчас иногда разнесены в несколько отдельных строк, хотя для N2 их лучше видеть как один review-group.
3. Для `drug_trade_name` и `supplement` canonical display иногда выбирает вариант с дозировкой, например `Берлиприл 20 мг`, вместо чистого бренда `Берлиприл`.
4. Product cleanup может быть опасным: одиночная буква `Г` может быть частью торгового названия, а не единицей граммов.
5. Голые числовые дозировки в названиях препаратов, например `Берлиприл 10`, `Берлиприл 20`, `Берлиприл 5`, сейчас могут не группироваться как варианты одного product name.
6. Болезни с `тип`, `типа`, `type`, `1 типа`, `2 типа`, `3A типа` должны быть явно защищены от схлопывания с базовой болезнью и между разными типами.
7. `context_only` сейчас сильно раздувает `suspicious_mentions`, хотя это скорее routing-сигнал, а не риск нормализации.
8. Нужно добавить отчёт по singleton candidate tags для будущего fast path.

N1.1 — это не новый этап LLM-нормализации. Это точечная доработка deterministic N1 перед N2.

## 2. Цель N1.1

Доработать deterministic normalization так, чтобы выход N1 стал пригоден для N2 candidate generation.

Основные цели:

- сделать `auto_clusters.csv` понятнее и убрать визуальные дубли review-mentions;
- добавить различие между безопасным auto-merge и review grouping;
- улучшить canonical display selection для лекарств и БАДов;
- усилить защиту болезней с типами/подтипами;
- разделить routing flags и risk flags;
- добавить singleton candidate report;
- обновить отчёты и тесты.

## 3. Не цели N1.1

На N1.1 запрещено:

- вызывать LLM;
- делать semantic merge;
- делать edit-distance clustering;
- делать embedding clustering;
- создавать финальные `tags_canonical.csv`;
- создавать финальные `tag_aliases.csv`;
- создавать `document_tag_links_normalized.jsonl`;
- начинать N2/N3;
- изменять `data/tagging/*`;
- исправлять failed documents;
- генерировать теги из `document_name`.

## 4. Обязательные изменения в модели auto-cluster

### 4.1 Добавить cluster status

В `AutoCluster` добавить поля:

```json
{
  "cluster_status": "auto_merged | review_group | isolated_mention",
  "merge_allowed": true,
  "blocking_flags": [],
  "routing_flags": [],
  "risk_flags": []
}

Значения:

auto_merged

Безопасный deterministic cluster. Можно считать, что mentions являются одной строковой сущностью.

Условия:

одинаковый entity_type;
одинаковый safe normalized key;
нет blocking flags;
нет опасных parent-child/type flags;
нет abbreviation risk;
нет low confidence;
нет quote issue как единственного подтверждения.
review_group

Несколько mentions имеют один нормализованный ключ или один review key, но auto-merge запрещён. Их нужно показывать вместе для N2/review.

Пример:

ARX
ARX
ARX

Не надо создавать 3 строки. Нужно создать одну строку:

cluster_status = review_group
merge_allowed = false
review_required = true
blocking_flags = very_short_alias; possible_abbreviation
isolated_mention

Один mention, который не объединён и не имеет других mentions с тем же review key.

5. Исправить дубли в auto_clusters.csv

Сейчас логика NO_AUTO_MERGE_FLAGS добавляет mention_id в group key, из-за чего одинаковые short aliases появляются в нескольких строках. Это безопасно, но неудобно и вредно для N2.

Новое правило

Не надо разносить mentions с одинаковым base key в разные rows только из-за NO_AUTO_MERGE_FLAGS.

Вместо этого:

grouped key должен оставаться общим;
cluster получает cluster_status=review_group;
merge_allowed=false;
review_required=true;
blocking_flags содержит причины, почему это не auto merge.

Пример:

biological_substance::arx

Если там 3 mentions, то должен быть один cluster:

{
  "auto_cluster_key": "biological_substance::arx",
  "cluster_status": "review_group",
  "merge_allowed": false,
  "mentions_count": 3,
  "review_required": true,
  "review_reasons": [
    "very_short_alias",
    "possible_abbreviation",
    "latin_only"
  ]
}
Acceptance check

После доработки в auto_clusters.csv не должно быть нескольких строк с одинаковыми:

entity_type + auto_cluster_key

Если одинаковый visual alias всё ещё встречается в разных строках, причина должна быть понятна: разные entity_type, разные subtype markers, разные product keys или разные parent/child protection keys.

8. Product cleanup: не удалять единицы без числа
Проблема

Сейчас г, мг, мл могут удаляться как отдельные токены. Это опасно, потому что буква Г может быть частью торгового названия.

Пример:

Гепатромбин Г

Нельзя превращать в:

Гепатромбин

если Г — часть бренда.

Новое правило

Удалять единицы измерения только вместе с числом:

20 мг
10 мл
2 г
5%

Не удалять одиночные:

г
мг
мл

как самостоятельные токены без числа.

Из form_terms удалить:

мг
мкг
мл
г

Оставить удаление этих единиц только через dosage regex, где есть число.

9. Product cleanup: голые числовые дозировки
Проблема

Некоторые лекарства имеют варианты:

Берлиприл 5
Берлиприл 10
Берлиприл 20

Если в raw tag нет мг, текущий regex может не понять, что это дозировка.

Новое правило

Для drug_trade_name и supplement добавить detection:

trailing_numeric_variant

Если название заканчивается на число или число + буква, например:

Берлиприл 5
Берлиприл 10
Берлиприл 20

то:

не обязательно auto-merge безоговорочно;
но нужно создать общий product_variant_group_key;
добавить risk flag possible_numeric_dosage_variant;
cluster должен быть review_group, если нет чистого alias;
если есть чистый alias Берлиприл, можно auto-merge в product cluster, но review_required=true.

Функция:

strip_trailing_numeric_product_variant(value: str) -> tuple[str, bool]

Примеры:

Берлиприл 20 → Берлиприл, changed=true
Берлиприл 5 → Берлиприл, changed=true
CoQ10 → CoQ10, changed=false
Q10 → Q10, changed=false
Витамин B12 → Витамин B12, changed=false

Важно: не ломать сущности, где число является частью бренда или вещества:

Коэнзим Q10
Витамин B12
IL-2
FGFR3
COVID-19

Для таких случаев добавить allowlist/pattern protection.

10. Disease subtype/type protection
Проблема

Много болезней содержат:

тип
типа
type
1 типа
2 типа
3A типа

Они должны оставаться отдельными тегами и не объединяться с базовой болезнью или другими типами.

Добавить флаг
has_type_subtype_marker

Для entity_type = disease, если строка содержит:

(?iu)\bтип(?:а)?\b
(?iu)\btype\b
(?iu)\b[0-9]+[a-zа-я]?\s*тип(?:а)?\b
(?iu)\bтип(?:а)?\s*[0-9]+[a-zа-я]?\b

Также ловить римские цифры:

I типа
II типа
III типа
IV типа
V типа
Добавить normalized subtype signature

Для disease mentions создать:

"subtype_signature": "type_1 | type_2 | type_3a | type_i | none"

Если subtype marker есть, auto_cluster_key должен учитывать subtype signature.

Пример:

GM1 ганглиозидоз тип 1
GM1 ганглиозидоз тип 2
GM1 ганглиозидоз тип 3

Должны быть разными clusters.

Запрет

Нельзя auto-merge:

болезнь X
болезнь X тип 1
болезнь X тип 2

Даже если строки похожи.

Review

Все disease clusters с has_type_subtype_marker должны иметь:

review_required = true
review_reasons includes has_type_subtype_marker
merge_allowed = false

Или merge_allowed=true только если exact same subtype signature and exact same normalized key.

Для N1.1 проще и безопаснее:

has_type_subtype_marker → review_required=true

20. Важное напоминание

N1.1 не должен решать semantic normalization.
