# Инструкция для агента: Pipeline Engineer — этап 1

## Роль в проекте

Ты Pipeline Engineer. Твоя задача — построить технический фундамент пайплайна первичной пересборки базы знаний: чтение `documents.csv`, генерация стабильных `doc_id`, парсинг Editor.js, сохранение очищенного текста и блоковой карты, базовая CLI-структура, логирование и отчёты.

Этот этап не занимается LLM-тегированием, нормализацией тегов, генерацией статей и загрузкой данных в систему. Твоя работа должна дать чистый, воспроизводимый и проверяемый вход для следующих агентов.

## Контекст проекта

В проекте есть около 16 000 старых документов. Каждый документ содержит `name`, `description`, `content`. Поле `content` — это Editor.js JSON. У документов нет стабильного ID, поэтому ID нужно сгенерировать.

Итоговая цель всего проекта — пересобрать старую базу из хаотичных документов в сущностную базу: болезни, лекарства, БАДы, симптомы, медицинские изделия, процедуры, диагностические методы, органы/системы и другие медицинские сущности. На этом этапе ты только готовишь корпус: извлекаешь текст и сохраняешь структуру.

## Главный результат этапа

После твоей работы должна появиться возможность выполнить команду парсинга и получить минимум два основных артефакта:

```text
data/parsed/parsed_documents.jsonl
data/parsed/document_blocks.jsonl
```

Также должны появиться базовый отчёт и технические логи:

```text
data/reports/run_report.json
data/logs/pipeline.log
```

Пайплайн должен поддерживать запуск на небольшом количестве документов:

```bash
python -m kb_rebuild parse --input data/input/documents.csv --out data --limit 100
```

Если в проекте уже есть другой утверждённый entrypoint или стек, используй его, но сохрани смысл команды: отдельный этап `parse`, явный input, явный output, возможность `--limit`.

## Входные данные

Ожидаемый файл:

```text
data/input/documents.csv
```

Если в проекте файл лежит в другом месте, не переноси его насильно. Реализуй CLI-параметр `--input`, чтобы путь можно было указать явно.

Ожидаемые колонки:

```text
name
description
content
```

`name` — важный контекст документа. Его нельзя игнорировать.

`description` на этом этапе сохраняется, но не используется для принятия решений.

`content` — строка с Editor.js JSON. Она может быть валидным JSON-объектом, JSON-строкой, пустой строкой, битым JSON или неожиданным форматом. Парсер должен быть устойчивым.

## Генерация doc_id

Так как стабильного ID нет, создай deterministic `doc_id` для каждой строки.

Рекомендуемый формат:

```text
doc_{row_index_1_based:06d}_{content_hash_8}
```

Пример:

```text
doc_000001_a1b2c3d4
```

Где:

- `row_index_1_based` — номер строки в CSV, начиная с 1;
- `content_hash_8` — первые 8 символов SHA-256 от исходного `content`;
- полный `content_hash` сохраняется отдельно.

Такой ID стабилен для текущей версии CSV и остаётся читаемым. Если обнаружены дубли `doc_id`, код обязан добавить безопасный суффикс и записать предупреждение в отчёт.

## Парсинг Editor.js

Парсер должен поддерживать минимум эти типы блоков:

```text
paragraph
header
list
table
quote
warning
checklist
delimiter
image
embed
code
raw
```

Также парсер должен корректно обрабатывать неизвестные типы блоков. Неизвестный блок нельзя молча выбрасывать. Для unknown-блока нужно попытаться извлечь текст из вложенных полей `text`, `caption`, `title`, `message`, `items`, `content`, `data` рекурсивно. Если текст найден, блок сохраняется с исходным `block_type`. Если текст не найден, блок всё равно учитывается в статистике как `empty_or_unhandled_block`.

### Правила извлечения текста

Для `paragraph`:

- взять `data.text`;
- удалить HTML-теги;
- сделать HTML-unescape;
- нормализовать пробелы.

Для `header`:

- взять `data.text`;
- сохранить уровень заголовка, если есть `data.level`;
- в `clean_text` заголовок должен быть отделён пустой строкой или явным переносом.

Для `list`:

- извлечь `data.items`;
- поддержать как массив строк, так и массив объектов;
- сохранить вложенность, если она есть;
- в `clean_text` представить списком с маркерами.

Для `table`:

- извлечь строки из `data.content`, если они есть;
- сохранить текстовую версию таблицы;
- допустимый формат: Markdown-like table или строки, разделённые табами;
- главное — не потерять содержимое ячеек.

Для `quote`:

- извлечь `data.text` и `data.caption`, если есть;
- сохранить оба текста.

Для `image` / `embed`:

- извлечь `caption`, `title`, `description`, если есть;
- URL не должен становиться основным текстом, но может быть сохранён в `raw`.

Для `delimiter`:

- текст не создаётся, но блок учитывается.

Для `code` / `raw`:

- сохранить содержимое как текст, если оно есть;
- не исполнять код.

## Выходной файл parsed_documents.jsonl

Каждая строка — один JSON-объект документа.

Минимальная схема:

```json
{
  "doc_id": "doc_000001_a1b2c3d4",
  "row_index": 1,
  "name": "Название документа",
  "description": "Описание или пустая строка",
  "content_hash": "sha256...",
  "parse_status": "ok",
  "parse_errors": [],
  "clean_text": "Очищенный текст документа",
  "text_length_chars": 12345,
  "blocks_count": 12,
  "non_empty_blocks_count": 10,
  "block_types": {
    "paragraph": 7,
    "header": 2,
    "table": 1
  }
}
```

Разрешённые значения `parse_status`:

```text
ok
partial
failed
empty
```

`failed` допустим только если невозможно извлечь вообще ничего. Даже при `failed` строка документа должна попасть в `parsed_documents.jsonl`, чтобы не потерять документ из отчёта.

## Выходной файл document_blocks.jsonl

Каждая строка — один блок документа.

Минимальная схема:

```json
{
  "doc_id": "doc_000001_a1b2c3d4",
  "block_id": "b_000001",
  "block_index": 0,
  "block_type": "header",
  "text": "Гастрит",
  "text_length_chars": 7,
  "metadata": {
    "level": 2
  },
  "raw_block_hash": "sha256...",
  "parse_status": "ok"
}
```

`block_id` должен быть уникален внутри документа. Рекомендуемый формат:

```text
b_{block_index_1_based:06d}
```

Если у блока есть исходный Editor.js id, сохрани его в `metadata.source_block_id`.

## CLI-команды

Минимально реализуй:

```bash
python -m kb_rebuild parse --input data/input/documents.csv --out data
python -m kb_rebuild parse --input data/input/documents.csv --out data --limit 100
python -m kb_rebuild validate-parsed --data data
```

`parse` создаёт артефакты.

`validate-parsed` проверяет:

- `doc_id` уникальны;
- каждый документ из CSV попал в `parsed_documents.jsonl`;
- каждый блок ссылается на существующий `doc_id`;
- `clean_text` является строкой;
- `parse_status` входит в разрешённый список;
- JSONL-файлы читаются без ошибок.

## Логирование

Пиши лог в:

```text
data/logs/pipeline.log
```

Лог должен содержать:

- старт и окончание этапа;
- путь входного файла;
- путь выходных файлов;
- количество документов;
- количество ошибок;
- предупреждения по битым или частично распарсенным документам.

Не логируй полный текст всех документов без необходимости.

## Тесты

Минимальный набор тестов:

1. Парсинг простого Editor.js с `paragraph` и `header`.
2. Парсинг `list`.
3. Парсинг `table`.
4. Парсинг неизвестного блока с вложенным текстом.
5. Обработка битого JSON без падения всего пайплайна.
6. Генерация уникального `doc_id`.
7. Проверка, что `document_blocks.jsonl` содержит блоки с правильным `doc_id`.

Запуск тестов должен быть описан в feedback.

## Ограничения

Не вызывай LLM.

Не нормализуй теги.

Не создавай статьи.

Не удаляй исходный CSV.

Не делай ручных предположений о медицинских сущностях.

Не останавливай весь прогон из-за одного битого документа.

## Критерии приёмки этапа

Этап можно принимать, если:

- есть CLI-команда парсинга;
- есть CLI-команда валидации распарсенных данных;
- `parsed_documents.jsonl` создаётся;
- `document_blocks.jsonl` создаётся;
- документы получают уникальные `doc_id`;
- заголовки, параграфы, списки и таблицы извлекаются;
- неизвестные блоки не теряются молча;
- ошибки парсинга записываются в отчёт;
- есть минимальные тесты;
- есть feedback-файл.
