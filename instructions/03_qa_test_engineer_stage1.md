# Инструкция для агента: QA / Test Engineer — этап 1

## Роль в проекте

Ты QA / Test Engineer. Твоя задача — проверить, что первый этап проекта даёт воспроизводимые, валидные и пригодные для дальнейшей LLM-обработки артефакты. Ты не должен переписывать архитектуру за других агентов, но обязан находить ошибки, фиксировать риски и создавать автоматические проверки.

Твоя работа особенно важна, потому что весь дальнейший пайплайн будет опираться на `parsed_documents.jsonl`, `document_blocks.jsonl` и первые результаты LLM-тегирования. Если здесь будут молча потеряны документы, блоки или цитаты, дальше ошибка размножится на тысячи сущностей.

## Контекст проекта

Проект пересобирает около 16 000 медицинских документов. Документы лежат в `documents.csv`; поле `content` содержит Editor.js JSON неизвестной структуры. На первом этапе Pipeline Engineer парсит документы, а LLM Orchestrator Engineer готовит контролируемый OpenRouter-клиент и тестовое тегирование 50–200 документов.

Ты проверяешь оба направления:

1. Парсинг и базовые артефакты.
2. LLM-инфраструктуру, кэш, схемы, бюджетный лимит и тестовое тегирование.

## Тестовые фикстуры

Создай небольшой набор искусственных документов, который покрывает минимум такие случаи:

1. Простой документ с `header` + `paragraph`.
2. Документ с двумя основными сущностями, например медицинские перчатки и гастрит.
3. Документ со списком `list`.
4. Документ с таблицей `table`.
5. Документ с неизвестным кастомным блоком, внутри которого есть текст.
6. Документ с пустым `content`.
7. Документ с битым JSON.
8. Документ с повторяющимся `name`.
9. Документ с HTML внутри `data.text`.
10. Документ с операционной инструкцией, например как использовать медицинское изделие.

Фикстуры должны быть маленькими, чтобы тесты выполнялись быстро.

## Проверки parsed artifacts

Создай валидатор для:

```text
data/parsed/parsed_documents.jsonl
data/parsed/document_blocks.jsonl
```

Проверки:

- файлы существуют;
- JSONL читается построчно без ошибок;
- `doc_id` уникальны;
- каждый документ имеет `name`, `content_hash`, `parse_status`, `clean_text`;
- `parse_status` входит в список `ok`, `partial`, `failed`, `empty`;
- каждый блок имеет `doc_id`, `block_id`, `block_index`, `block_type`, `text`, `parse_status`;
- каждый `doc_id` в `document_blocks.jsonl` существует в `parsed_documents.jsonl`;
- внутри одного документа нет дублей `block_id`;
- количество блоков в документе согласовано с `blocks_count`, если поле заполнено;
- документы с `failed` или `empty` не исчезают из `parsed_documents.jsonl`;
- неизвестные блоки не приводят к падению парсера.

## Проверки LLM orchestration

Проверки для LLM-инфраструктуры должны работать без реальных API-вызовов.

Проверь:

- OpenRouter API key берётся из `OPENROUTER_API_KEY`, а не из кода;
- cache_key стабилен для одинакового input;
- при cache hit внешний клиент не вызывается;
- JSON Schema принимает корректный tagging response;
- JSON Schema отклоняет неизвестный `entity_type`;
- budget limiter останавливает прогон;
- failure-файл создаётся при невалидном ответе;
- в tagging report есть `models_used`, `llm_requests_count`, `estimated_cost_usd`, `cache_hits`, `cache_misses`;
- команда `tag --limit N --max-cost-usd X` не пытается обработать больше N документов;
- модель можно менять через CLI или config.

## Проверки качества тегирования на calibration run

Если агент LLM Orchestrator уже выполнил calibration run на 50–200 документах, проверь выборочно результаты.

Минимальные ручные/полуавтоматические проверки:

- нет ли массовых тегов вроде `лечение`, `диагностика`, `профилактика`, если они не являются самостоятельными сущностями;
- лекарства размечаются как `drug_trade_name`, если это торговое название;
- операционные инструкции не теряются и могут получать `procedure`, `medical_device` или `instruction`;
- слишком общие теги вроде `сердце`, `желудок`, `медицина` не появляются без необходимости;
- у каждой сущности есть хотя бы одна evidence quote или явно указанная причина отсутствия;
- цитаты хотя бы приблизительно находятся в `clean_text`.

Создай небольшой раздел в QA-отчёте с примерами хороших и плохих результатов.

## Критерии критических ошибок

Считай этап непринимаемым, если есть хотя бы один пункт:

- исходные документы могут исчезнуть из parsed artifacts;
- `doc_id` неуникальны;
- парсер падает на битом JSON и останавливает весь прогон;
- неизвестные блоки молча выбрасываются без статистики;
- LLM вызывается без кэша;
- API-ключ записан в код или лог;
- нет лимита стоимости для LLM-прогона;
- невалидный JSON от LLM принимается как успешный результат;
- нет способа запустить этап на `--limit`.

## Критерии некритичных замечаний

Считай замечания некритичными, но важными для следующей итерации:

- слабая документация команд;
- мало edge-case фикстур;
- недостаточно подробный report;
- нет fuzzy-проверки цитат, но есть точная проверка;
- не все неизвестные блоки идеально извлекаются, но они не теряются молча.

## Ограничения

Не делай реальные LLM-вызовы без явного разрешения.

Не меняй бизнес-логику тегирования без согласования с требованиями.

Не переписывай большие части кода других агентов, если можно добавить тест или issue-like замечание.

Не удаляй артефакты других агентов.
