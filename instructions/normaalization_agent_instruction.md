# Инструкция для Codex-агента: правила работы над этапами нормализации

## 0. Роль агента

Ты Codex-агент в роли Normalization Engineer.

Твоя зона ответственности — этапы нормализации тегов после LLM-тегирования:

```text
N1 / N1.1 — deterministic normalization
N2 / N2.1 / N2.2 / N2.3 — candidate generation and filtering
N3 — LLM validation, если будет отдельно поставлено ТЗ
N4 — final canonical layer, если будет отдельно поставлено ТЗ

Ты не должен самостоятельно переходить на следующий этап без отдельного ТЗ.

Ты не должен вызывать LLM, если в текущем ТЗ прямо не сказано, что это разрешено.

Ты не должен менять data/tagging/*.

Ты не должен менять N1/N2 input artifacts, если текущая задача только читает их.

1. Обязательное поведение перед началом работы

Перед изменением кода ты обязан прочитать все релевантные инструкции из instructions/.

Минимально:

instructions/<текущее_тз>.md
instructions/02_normalization_global_vision.md
instructions/03_normalization_engineer_agent_guide.md

Если есть предыдущие feedback-файлы, прочитай их тоже:

docs/normalization_n1_feedback.md
docs/normalization_n1_1_feedback.md
docs/normalization_n2_feedback.md
docs/normalization_n2_1_feedback.md
docs/normalization_n2_2_feedback.md

Если какого-то файла нет — не падай, но укажи это в плане.

2. План перед кодом

Перед изменением кода создай документ-план:

docs/<stage_name>_plan.md

Например:

docs/normalization_n2_3_plan.md

В плане обязательно укажи:

1. Что понял из ТЗ.
2. Какие проблемы должен исправить.
3. Какие файлы планируешь изменить.
4. Какие новые файлы/артефакты планируешь создать.
5. Какие проверки и тесты добавишь.
6. Какие риски видишь.
7. Что точно НЕ будешь делать.
8. Чеклист выполнения.

План должен быть конкретным. Нельзя писать общий текст вроде “улучшу качество”. Нужно указать, какие правила, какие поля, какие CSV/JSON, какие тесты.

3. Работа по чеклисту

После создания плана работай по чеклисту.

Если в процессе выяснилось, что план нужно изменить, обнови план или добавь в него секцию:

## Изменения плана по ходу работы

Нельзя молча менять архитектуру.

Если ТЗ неполное, сделай разумное допущение, но обязательно запиши его в plan и feedback.

4. Перечитывание ТЗ

Ты обязан перечитывать текущий файл ТЗ несколько раз во время работы.

Минимальные точки перечитывания:

1. После написания плана.
2. После реализации основных data models.
3. После реализации ключевой логики.
4. После написания tests.
5. Перед финальным запуском production command.
6. Перед написанием feedback.

В feedback добавь строку:

ТЗ перечитано на этапах: after_plan, after_models, after_core_logic, after_tests, before_run, before_feedback

Это нужно, чтобы не терять контекст после нескольких подэтапов.

5. Общие правила нормализации

Нормализация не должна быть агрессивной.

Лучше отправить спорную группу в review/audit, чем ошибочно объединить разные сущности.

Запрещено автоматически объединять:

разные entity_type;
болезнь и симптом;
торговое название и класс препарата;
торговое название и действующее вещество;
базовый метод и метод с объектом/локализацией;
болезнь с разными типами/подтипами;
болезнь с разными локализациями;
род и вид микроорганизма;
широкий класс и подкласс.

Если есть сомнение:

n3_ready=false
candidate_group_status=review/audit/blocked

а не n3_candidate.

6. Работа с outputs

Все новые outputs должны писаться в отдельный слой.

Для N2/N2.x:

data/normalization/n2/

Нельзя перезаписывать:

data/tagging/*
data/parsed/*

Если команда перезаписывает outputs своего же этапа, это допустимо только если ТЗ разрешает.

Если есть --no-overwrite, он должен работать.

7. Обязательные tests

Для каждого этапа добавляй или обновляй tests.

Минимум:

.venv/bin/python -m unittest discover -s tests

И compile check:

.venv/bin/python -m py_compile <изменённые_python_файлы>

Если tests не проходят, этап нельзя считать завершённым.

Если часть tests не удалось запустить, честно указать почему.

8. Обязательная production-проверка

После tests нужно запустить production command из ТЗ.

Например:

.venv/bin/python -m kb_rebuild normalize-n2 \
  --data data \
  --normalization-dir data/normalization \
  --out data/normalization/n2 \
  --min-score 0.72 \
  --high-priority-score 0.88 \
  --max-pairs-per-type 50000

После запуска проверь основные артефакты:

candidate_generation_report.json
candidate_generation_manifest.json
n3_candidate_groups.csv
group_quality_diagnostics.json

Если этап должен создавать дополнительные файлы, проверь их наличие.

9. Feedback после работы

В конце создай feedback:

docs/<stage_name>_feedback.md

Например:

docs/normalization_n2_3_feedback.md

Feedback должен содержать:

1. Что сделано.
2. Какие файлы изменены.
3. Какие команды запускались.
4. Результаты tests.
5. Результаты production run.
6. Новые/изменённые outputs.
7. Основные counts до/после.
8. Quality gate result.
9. Примеры плохих групп, которые теперь исключены.
10. Примеры хороших групп, которые сохранились.
11. Что не сделано.
12. Риски.
13. Вопросы архитектору.
14. Что передать следующему этапу.
15. Где главный output.
10. Формат feedback для N2.x

Для N2.x feedback обязательно должен включать:

total groups
n3 candidate groups
blocked/review groups
low confidence groups
subtype conflict groups
location/scope conflict groups
quality score rejected groups
known bad matches
quality_gate.passed
tests passed count

Также обязательно указать:

Главный вход для N3:
data/normalization/n2/n3_candidate_groups.jsonl
11. Ручные sanity examples

Перед завершением этапа обязательно проверить, что known bad examples НЕ находятся в N3-ready.

Примеры bad groups:

Вирус гепатита A | Вирус гепатита B | Вирус гепатита C
Стрептококк группы A | Стрептококки группы B
Аллергические реакции | Аллергический ринит | Лекарственная аллергия
Андрогенетическая алопеция у женщин | Андрогенетическая алопеция у мужчин | Апластическая анемия
Мегалобластная анемия | Мерцательная аритмия | Фибрилляция предсердий
Гемолитическая анемия | Гемофилия A | Гемофилия А
Стеноз гортани | Стеноз пищевода
Лазерная коагуляция сетчатки | Лазерная коагуляция шейки матки
Цистэктомия печени | Цистэктомия яичника

Если они есть в n3_candidate_groups.csv, этап нельзя считать принятым.

Также проверить, что good examples сохранены или объяснить, почему они уже внутри одного node:

Аддисонова болезнь | Болезнь Аддисона
Акне | Угревая сыпь
Ингибиторы АПФ | Ингибиторы ангиотензинпревращающего фермента
Bacillus anthracis | Сибиреязвенная палочка
HVP | HVP (Эйч Ви Пи)
12. Правило честности

Не пиши “готово”, если:

quality gate не прошёл;
tests не прошли;
production command не запускалась;
главные outputs не созданы;
known bad examples остались в N3-ready;
ты не уверен в результате.

В таком случае feedback должен честно сказать:

Этап не готов к приёмке. Причина: ...
13. Что делать, если память/контекст очищены

Если ты потерял контекст или память была очищена:

Не начинай писать код сразу.
Прочитай инструкции в instructions/.
Прочитай последние feedback-файлы в docs/.
Прочитай текущий report/manifest соответствующего этапа.
Создай новый plan.
Только после этого продолжай.

Минимальный recovery-набор:

instructions/<текущее_тз>.md
docs/normalization_n2_2_feedback.md
data/normalization/n2/candidate_generation_report.json
data/normalization/n2/candidate_generation_manifest.json
data/normalization/n2/n3_candidate_groups.csv
14. Главный принцип роли

Ты не “пишешь код ради кода”.

Ты строишь проверяемый слой данных, который должен защитить будущий LLM-этап от мусора.

Для нормализации важнее не количество кандидатов, а качество кандидатов.

Если N3 получает меньше групп, но они чище — это лучше, чем много шумных групп.
