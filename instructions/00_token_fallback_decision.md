# Решение архитектора: удешевление токенов и fallback DeepSeek → Gemini

## Контекст

На текущем этапе тегирования есть две разные проблемы:

1. DeepSeek V4 Flash дешёвый, но текущий route через OpenRouter нестабилен и/или медленный. При ошибке 429 нельзя уходить в долгий sleep, если есть быстрый Gemini route.
2. Gemini 3 Flash Preview показывает хорошую скорость, но стоимость выше. Нужно уменьшить input/output tokens без потери качества тегирования.

## Архитектурное решение

Для production-тегирования вводим гибридную схему:

- `deepseek/deepseek-v4-flash` может использоваться как дешёвый primary только пока он здоровый и быстрый.
- `google/gemini-3-flash-preview` становится быстрым fallback, а при необходимости — production primary.
- Если DeepSeek возвращает HTTP 429, система не должна ждать долгий backoff перед следующим документом. Она должна немедленно отправить текущую задачу в Gemini и поставить DeepSeek route в cooldown.
- Если DeepSeek route в cooldown, новые задачи сразу идут в Gemini до окончания cooldown.
- Если Gemini получает 429, тогда применяется обычный adaptive cooldown, потому что Gemini является быстрым production route.

## Текущая оценка экономики

По 42 доступным результатам текущего DeepSeek-прогона:

- средний input: около 1757 prompt tokens на документ;
- средний output: около 711 completion tokens на документ;
- средняя стоимость DeepSeek Flash: около $0.00045 на документ;
- оценочная стоимость Gemini 3 Flash Preview при тех же tokens: около $0.0030 на документ;
- оценочная стоимость Gemini на весь корпус 16 181 документов: около $49 без оптимизаций и retries.

Если уменьшить output Gemini на 30–50%, ожидаемая стоимость полного тегирования может снизиться примерно до диапазона $31–38. Это важнее, чем небольшое уменьшение input, потому что у Gemini output значительно дороже input.

## Главный источник экономии

Нужно уменьшать не качество рассуждения, а размер JSON-ответа.

Текущий output содержит много полей, которые можно убрать или перенести на более поздние этапы:

- `comment` — убрать из LLM output;
- `canonical_candidate_latin` — перенести на этап нормализации тегов;
- `is_primary` — убрать, потому что prompt уже требует возвращать только основные сущности;
- `evidence_quotes` как массив — заменить на одну строку `q`/`evidence_quote`;
- длинные имена полей — заменить на компактные ключи во внутреннем LLM-контракте и затем расширять кодом.

## Новый компактный LLM-контракт

Для one-document mode:

```json
{
  "d": "doc_000123_abcd1234",
  "e": [
    {
      "s": "поверхностная форма из документа",
      "ru": "Канонический кандидат на русском",
      "t": "entity_type",
      "r": "article",
      "c": 0.93,
      "q": "одна короткая дословная цитата"
    }
  ]
}
```

Для batch mode:

```json
{
  "docs": [
    {
      "d": "doc_000123_abcd1234",
      "e": []
    }
  ]
}
```

Код обязан расширять компактный контракт в человекочитаемый downstream-формат:

```json
{
  "doc_id": "doc_000123_abcd1234",
  "entities": [
    {
      "surface": "...",
      "canonical_candidate_ru": "...",
      "canonical_candidate_latin": "",
      "entity_type": "...",
      "tag_role": "article",
      "confidence": 0.93,
      "evidence_quotes": ["..."],
      "comment": ""
    }
  ]
}
```

## Новые типы сущностей

К существующим типам нужно добавить:

- `drug_class` — классы лекарств, например макролиды, тетрациклины, бета-лактамные антибиотики;
- `immunobiological_preparation` — вакцины, иммунобиологические препараты;
- `biological_substance` — лизоцим, интерфероны, пропердин, фибронектин;
- `microorganism` — бактерии, вирусы, прионы, вироиды, конкретные виды микроорганизмов;
- `cell_or_biological_structure` — клеточная стенка, рибосомы, Т-лимфоциты, В-лимфоциты, NK-клетки.

Важно: `drug_trade_name` использовать только для торговых/коммерческих названий препаратов и вакцин.

## Batch mode

Нужно реализовать batch tagging. Один запрос должен обрабатывать несколько документов.

Начальные параметры:

```text
batch_size = 5
max_inflight = 1
```

После стабильного benchmark можно пробовать:

```text
batch_size = 8-10
max_inflight = 2
```

Batch mode должен сохранять результат отдельно по каждому документу. Если один документ внутри batch невалиден, валидные документы не теряются, а проблемный документ уходит в singleton retry.

## Критерии готовности

Этап считается готовым, если:

- реализован compact schema;
- реализован expanded downstream output;
- реализован batch mode;
- реализована немедленная маршрутизация DeepSeek 429 → Gemini;
- реализован cooldown/circuit breaker для DeepSeek;
- есть отчёт сравнения current schema vs compact schema;
- есть отчёт сравнения DeepSeek-only, Gemini-only и hybrid DeepSeek→Gemini;
- QA даёт verdict, какую схему запускать на полном корпусе.
